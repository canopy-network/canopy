# Push-Alert Webhooks

**In one sentence:** an optional, fire-and-forget webhook that pushes a notification when one
of three risky on-chain conditions crosses a threshold — so operators don't have to sit and
poll the API.

The [HTTP API](../api/endpoints.mdx) lets you *pull* protocol state whenever you like. Push
alerts add the opposite: an *unattended* path for the handful of events someone genuinely
needs to react to fast. Alerts are **off by default** and enabled by configuring a webhook
URL.

## The conditions

| Alert | Fires when… | Window | Severity | Default threshold |
|-------|-------------|--------|----------|-------------------|
| `buyback_drain` | the buyback pool shrinks too fast | tumbling | `warn` | 5,000 bps (50%) |
| `validator_concentration` | one validator holds too much committee stake | instantaneous | `warn` | 6,600 bps (66%) |
| `tvl_drop` | total pooled CNPY falls too fast | tumbling | `crit` | 2,000 bps (20%) |
| `reward_attribution_anomaly` | one block credits an implausible amount of reward | instantaneous | `crit` | 100 bps (1%) |
| `owned_stake_missing` | the committee is earning but canoLiq owns none of it | instantaneous | `warn` | — |
| `owned_bond_not_compounding` | a canoLiq-owned bond pays out instead of compounding | instantaneous | `warn` | — |

The three reward-attribution alerts are worth reading together, because they
cover the two ways the exchange rate can be wrong.

**`reward_attribution_anomaly`** is the backstop on crediting too much. It
compares one block's attributed reward against the larger of pooled CNPY and
owned stake. Real committee reward is a fraction of a basis point per block, so
1% is orders of magnitude of headroom. For calibration: the mainnet committee-29
incident that motivated this ran at 11,900 bps, meaning it would have paged on
the first bad block rather than being noticed forty minutes later.

**`owned_stake_missing`** covers crediting nothing. Attributing zero reward is
correct when canoLiq owns no bonded position — see
[how it works](../concepts/how-it-works.mdx) — but it must not be
indistinguishable from a healthy chain having a quiet block. This fires when the
committee is compounding, cCNPY is outstanding, and none of the stake earning it
is canoLiq's. It is a `warn` because nothing is lost or mis-credited; the
protocol simply is not earning, and the fix is operational.

**`owned_bond_not_compounding`** covers earning invisibly. Canopy only adds
reward to a bond's stake when the record is compounding and not unstaking;
otherwise it pays out to the bond's output address as liquid CNPY, where the
stake-growth observation cannot see it. The reward is real and recoverable by
hand, just not through the exchange rate. Set `compound=true` on the bond.

- **Tumbling window:** the protocol records a baseline at the start of each window
  (`window_blocks`, default 100) and compares the current value against it. A drop larger
  than the threshold fires the alert. When the window elapses, a fresh baseline is taken.
- **Instantaneous:** the rest are state checks run every block, with no window — validator
  concentration as `max validator stake ÷ total committee stake`, and the three
  reward-attribution conditions against the current globals and registry.

## Debounce: no alert storms

A firing condition would otherwise re-page every single block. To prevent that, each alert
kind keeps a **watermark** (`last_fired_height`) in state:

- After firing, the alert stays quiet for at least `min_interval_blocks` (default 100 blocks).
- The watermark **clears the moment the condition resolves**, so a *new* occurrence later
  fires immediately rather than waiting out the debounce.
- Because the watermark lives in state, it survives plugin restarts.

## Delivery is best-effort and never blocks consensus

Alerts are evaluated during `EndBlock`, but delivery happens **off-thread**: the webhook POST
runs in a goroutine with a 5-second timeout. A slow or dead receiver can never stall block
production. Failures are logged at `WARN` and otherwise ignored — alerts are advisory, not
guaranteed.

## Payload formats

The canonical payload is the **`AlertEnvelope`**, sent verbatim when `format` is `json`:

```json
{
  "kind": "tvl_drop",
  "height": 84210,
  "severity": "crit",
  "message": "TVL dropped faster than threshold",
  "details": {
    "baseline": 1050000000,
    "current": 800000000,
    "dropBps": 2381,
    "thresholdBps": 2000,
    "schemaVersion": 1
  }
}
```

`details` is condition-specific and always carries a `schemaVersion` for downstream
consumers. For `slack` and `discord` formats, the envelope is projected into that platform's
shape — a single human-readable line such as:

```
[crit] canoLiq tvl_drop @ h84210: TVL dropped faster than threshold
```

sent as `{"text": "…"}` (Slack) or `{"content": "…"}` (Discord).

## Configuration

Alerts are configured under the `alerts` block of the plugin config JSON (or `CANOLIQ_ALERT_URL`
to override the URL at startup). An empty `webhookUrl` disables the whole subsystem.

| Field | Purpose | Default |
|-------|---------|---------|
| `webhookUrl` | POST target; empty disables alerts | — (disabled) |
| `authHeader` | sent as the `Authorization` header | — |
| `format` | `json`, `slack`, or `discord` | `json` |
| `windowBlocks` | tumbling-window size for drain/drop | 100 |
| `defaultMinIntervalBlocks` | debounce when a kind has no override | 100 |
| `minIntervalBlocks` | per-kind debounce overrides (map) | — |
| `drainAlertBps` | buyback-drain threshold | 5,000 (50%) |
| `concentrationAlertBps` | validator-concentration threshold | 6,600 (66%) |
| `tvlDropBps` | TVL-drop threshold | 2,000 (20%) |
| `rewardAttributionBps` | one-block reward-attribution threshold | 100 (1%) |

```json
{
  "alerts": {
    "webhookUrl": "https://hooks.example.com/canoliq",
    "format": "slack",
    "windowBlocks": 100,
    "tvlDropBps": 1500,
    "minIntervalBlocks": { "tvl_drop": 50 }
  }
}
```
